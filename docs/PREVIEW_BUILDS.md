# Промежуточные HTML-сборки Pull Request

Этот процесс экономит лимиты Work/Astra: GitHub Actions самостоятельно собирает
архив с запускаемой HTML-версией из **конкретного PR**. Искусственный интеллект
не требуется для упаковки. Это не стабильный релиз.

## Как получить промежуточную сборку

1. Открой PR в репозитории `bunkovde-lab/developer-web`.
2. Перейди на вкладку **Checks** (или GitHub Actions, workflow
   **Package Developer Web PR preview**).
3. Дождись завершения job `preview-package`.
4. В разделе **Artifacts** скачай `developer-preview-<номер PR>`.
5. Распакуй архив. Файл `BUILD_INFO.txt` содержит SHA сборки и SHA исходной ветки.

Для запуска на компьютере из распакованной папки:
```bash
python -m http.server 8000
```
Затем открой `http://localhost:8000`. На смартфоне можно открыть тот же
локальный сервер через Wi-Fi по локальному IP компьютера, если разрешён
доступ из локальной сети. Не выставляй тестовый сервер в интернет.
Открытие `index.html` непосредственно из файлового менеджера может не
работать в некоторых браузерах — предпочитай локальный HTTP.

**Важно:** файлы сборки скачиваются из GitHub Actions; это НЕ публичная
онлайн-ссылка на тестовую версию, не APK и не публикация GitHub Pages.

## Технический контракт

- Для PR в `main` и ручного запуска workflow собирает папку `preview/`:
  `index.html`, актуальные игровые JS/CSS-модули и `assets/**`.
- Проверяет наличие подключённых `<script src>` и `<link href>`.
  Отсутствующий файл приводит к ошибке workflow.
- Публикует архив на 14 дней. Сохранение архива не гарантировано вечно.
- Автосборка дополняет, но не заменяет Node-тесты, Chromium UI,
  симуляции QA и ручную проверку на реальном устройстве.
- Основная проверенная публикация остаётся GitHub Pages из `main`.
- **Programm** проверяет полный набор статусов CI и выпускает релиз только
  через стандартный PR-процесс.
- **Work** стоит запускать по новым блокирующим ошибкам и готовым PR,
  а не для повторения автоматической упаковки.
- **Astra** — для сложного архитектурного/экономического аудита по необходимости.

## Контроль перед merge

Проверь `node-tests`, `browser-ui`, `preview-package`;
сопоставь SHA в `BUILD_INFO.txt` с PR. Красные проверки блокируют merge.
Проверяющий должен описать ограничения тестирования в отчёте.
