# Developer Web — протокол интеграции QA, SVG и Programm

**Источник истины:** `bunkovde-lab/developer-web`, защищаемая ветка `main`. Этот файл описывает *рабочий процесс*, а не вводит новые правила игры. Актуальная реализация — содержимое `main`; действующее описание механик — `docs/ACTIVE_GAME_SPEC_v016.md`. Исторические документы не подменяют код. Перед каждой интеграцией проверить текущий HEAD и открытые PR.

## Ответственность

| Участник | Ветки / области | Результат |
| --- | --- | --- |
| Programm (интегратор) | `main`, `integration/<issue>-<topic>`, интеграционные правки движка | Ревью, разрешение конфликтов, прохождение CI, merge и выпуск |
| QA | `qa/<issue>-<topic>`; `tests/**`, `docs/qa/**`, при необходимости точечные поправки экономики | Тесты, сценарии, численные результаты, воспроизведение, PR |
| SVG | `svg/<issue>-<topic>`; `assets/svg/**`, `assets/svg/manifest.json`, `docs/art/**` | Чистые SVG, дизайн-спецификация, примеры, PR |

Ветки — **на одну задачу**, не постоянно расходящиеся копии приложения. QA/SVG не меняют `main` напрямую; если для работы требуется код движка — показывают патч в своём PR и поясняют его. Никогда не удалять несвязанные изменения другой команды при разрешении конфликтов.

## Обязательная схема

1. **Programm открывает итерацию:** сравнивает `main` с последней подтверждённой версией, проверяет `git status`, ветки `qa/*` и `svg/*`, открытые PR, конфликты и статусы Actions; записывает HEAD SHA в отчёт.
2. **QA** ответвляется от актуального `main`. Для экономики прикладывает: дифф конкретных формул, неизменяемые утверждённые правила, воспроизводимые seed, сравнительную таблицу "до/после" для 3–6 игроков, проверки 2 действий, ограничения карт, аукционов, полного цикла, сохранений и банкротства. Прилагает выводы о смещении стратегии и остановках; одни лишь `16/16` без распределений не доказывают баланс.
3. **SVG** ответвляется от актуального `main`; сдаёт отдельные `.svg` в `assets/svg/` и обновляет `manifest.json` с ключами использования. Поставляет единый `viewBox`, масштабирование, контраст и touch-варианты, несколько контрольных снимков 390×844, 768×1024, 1024×768, 1366×900. Художественный PR не меняет экономику или код игры без отдельного обоснования.
4. **PR на `main`** маркируется `qa`, `svg` или `integration` и содержит описание воздействия, тесты, ограничения, снимки для UI, а также ссылки на связанные issues. До merge PR обновлён относительно `main` и имеет зелёный CI. Для нового/заменяемого SVG описывается соответствующий ключ манифеста.
5. **Programm проводит интеграцию:** сначала сливает независимые валидные PR, затем в отдельном `integration/*` PR связывает SVG-ключи с DOM/CSS и решает конфликты; не допускает перезаписи обновлённого `index.html` устаревшей копией. Экономика отделяется от визуала; если конфликт затрагивает общие API, согласует контракт до merge.
6. **Регрессионные ворота:** синтаксис JS → `tests/smoke.cjs` → `tests/territory.cjs` → `tests/city-requests.cjs` → `tests/pace.cjs` → `tests/rework.cjs` → `tests/tournament-v016.cjs` → `tests/svg-assets.cjs` → браузерные тесты Chromium. Любой красный тест блокирует merge. Запрет на пропуск/удаление тестов ради зелёного CI без отдельного анализа.
7. **Проверка полной партии:** автопрогоны, проверка границ победы и расчётов; затем ручная партия хотя бы на одном реальном устройстве при изменении UI/потока действий. Полная ручная проверка не может считаться выполненной на основе симулятора. Отчёт содержит число ходов, исход, ошибки консоли, шаги и версию.
8. **Выпуск:** после успешного merge `main` публикуется GitHub Pages; Programm проверяет Actions `Publish Developer Web`, что код последнего SHA реально попал в публикацию, а также URL новой игры и отсутствие ошибок. В changelog отчёте: SHA/PR, изменённые файлы, пройденные тесты, известные ограничения и ссылка на запуск.

## Каталоги и контракт SVG

```text
index.html                 точка входа / UI и игровое состояние
balance.js                 экономика, боты, рынок карт, строительные действия
pace.js                    экспериментальный темп
auction-competition.js     механизм земельных аукционов
city-requests.js           предложения города на «Сделке»
marketplace.js             биржа карт и переговоры
game-rework-v016.js        дополнительные механики версии v0.16
visual.js / visual.css     визуальное отображение и управление
assets/svg/
  README.md                стандарт ассетов
  manifest.json            ключ → относительный путь до файла
  lots/                    символы земли и застройки
  buildings/               сооружения и стадии проекта
  cards/                   иллюстрации и иконки карт
  ui/                      системные пиктограммы
tests/                      игровые, браузерные и SVG-проверки
docs/qa/                    отчёты QA, seed, таблицы и методика
docs/art/                   палитра, размеры, снимки, арт-протокол
.github/workflows/          регрессии, браузерный UI, публикация
```

Правило для `manifest.json`: `{"version":1,"assets":{"lot.j1":"assets/svg/lots/j1.svg"}}`. Ключи — стабильные контракты между художником и программистом; **изменение имени ключа — breaking change** и требует отдельной миграции. Новые ассеты добавляются без уничтожения старых ключей, пока интерфейс не переведён. Сам манифест ничего не отображает — Programm отдельно подключает ассеты к интерфейсу.

SVG должен иметь собственный `viewBox`, не содержать внешних ресурсов, JS, `foreignObject`, растровых вставок и необязательных шрифтов. Векторный asset PR проверяется `node tests/svg-assets.cjs`, а конечная интеграция — браузером. Разрешены только относительные пути внутри `assets/svg`; ресурс по HTTPS не является заменой файла в репозитории.

## Ворота для защиты `main`

Рекомендация в GitHub Settings → Branches / Rulesets:

- Require a pull request before merging; минимум один ревьюер (Programm) и актуальная ветка.
- Require status checks: `node-tests`, `browser-ui` (и отдельно SVG-validation, если выделена в job).
- Block force push и удаление `main`. Не допускать push напрямую, кроме аварийного исправления с последующей ретроспективой.
- Prefer squash merge и идентификатор issue/PR в сообщении; резервная релизная точка — тег после проверки.

Правила защиты устанавливаются владельцем в GitHub UI: наличие этого документа **не включает** их автоматически.
