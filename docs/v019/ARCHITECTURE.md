# v0.19 — аудит и целевая архитектура

База: main `c86df7daac15172fcea3afdc2a94a7ca0265b468`, с интегрированными PR #11, #14 и #15. Ветка разработки: `work/rebuild-v019`. Main не изменяется.

## Реестр до переработки

Машиночитаемый реестр `game/feature-contract.json` фиксирует все именованные функции исходного inline-ядра, хеш исходника, 12 семейств механик и существующие проверки. `node tests/feature-contract.cjs` проверяет сохранение поверхности ядра и наличие тестов. Это не замена поведенческим тестам.

Действующие правила: 24 участка 6×4, 32 клетки, 2d6, 3–6 участников; физические колоды с немедленным возвратом, два основных действия и договорная сделка; строительство 0–4, инженерные подключения, аренда на Старте, продажа, инвестиционный waterfall и остаточный долг; закрытые аукционы, торговля картами и землёй; профессии, боты и три действующих способа окончания партии. Экономические параметры не меняются.

Источники правил: `docs/ACTIVE_GAME_SPEC_v016.md`, фактический JavaScript, `WORK_CONTROL_V018.md`, `WORK_RC1_TECHNICAL.md`, QA Issue #16. Числа из исторических документов не заменяют актуальный код. UI по-прежнему локальный: один человек и 2–5 ботов. Мультиплеер и APK не входят в v0.19.

## Решение

1. Перенести inline-ядро без переписывания формул в предметные файлы `game/core/`: каталог, состояние/ходы, земля/аукционы, карты/события, строительство/сети, финансы/сделки, отображение, сохранение и лобби.
2. Явный `game/core-manifest.json` определяет загрузку. Обычные script-файлы сохраняют совместимость существующих расширений; смена модульной системы и экономическая правка одновременно запрещены внутренним gate этой итерации.
3. Отделить существующее поведение ботов от финансового слоя через фабрику с явно переданными зависимостями. Сохранить порядок вызовов, RNG и условия решений.
4. Публичный runtime предоставляет команды, неизменяемую проекцию состояния и ограниченную диагностику. Представление использует runtime и не записывает экономическое state. Эффекты не определяют завершение действий или ходов.
5. UI-компоненты: поле, панель текущего хода, кабинет с активами/обязательствами, инвентарь, журнал, согласованные диалоги. Дизайн — графит/синий/золото, существующая SVG-библиотека; новая изометрия v2 не создаётся.
6. Сохранения старого формата читаются; v0.19 использует собственный storage key, чтобы тестовый URL на одном origin не перезаписал сохранение стабильной версии. Импорт из прежнего ключа — явный пользовательский шаг.

## Проверки сохранения

- Все прежние Node- и браузерные тесты работают с общим загрузчиком модульного ядра; тесты не получают альтернативную копию игровых правил.
- Исходный и новый движки запускаются на одинаковых seeds. Сравниваются исходы, деньги, готовые проекты, торговые показатели и диагностические snapshots, а не только число побед.
- Полные браузерные партии запускаются через настоящую цепочку таймеров ботов с восстановлением в середине; отдельно проверяются stale callbacks, Storage denial, fallback SVG, анимации и touch.
- Компоновка проверяется на 390×844, 768×1024, 1024×768, 1366×900, дополнительно на горизонтальном телефоне. Скриншоты UI-фикстуры и полного цикла подписываются раздельно.
- 805/1000 — исследовательская задача QA. Числа и причины фиксируются; цены, AI-стратегии и пороги не подстраиваются ради улучшения оценки.

## Ограничения архитектуры

Переход сохраняет browser-global ABI для существующих динамических карточек. Это осознанная совместимость, не заявление о полностью устранённых глобальных функциях. Следующая миграция к ES modules возможна после проверенного v0.19, с отдельным сравнением. Доступность всех диалогов и производительность физического Android требуют реального тестирования, а не заявления по скриншотам.
